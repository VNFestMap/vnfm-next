# 重构模块划分

原站乱，不是因为功能少，而是因为 **没有模块边界**：根目录几十个 HTML 各自为政，同好会既在 JSON 又在 SQL，广场/用户中心把所有东西拼在一页里，GalOnly、萌战、Wiki 全直接读 `clubs.json`。

上一份 `01 / 02 / 03` 是 **功能清单的阅读顺序**，不是重构边界。按模块重构时，以本文为准。

结论先说：**不要按页面切，按领域切。** 对外只保留 5 个业务大模块，底下一个内核，旁边一个卫星仓。页面（地图、用户中心、广场、社团详情）是这些模块的组合层，自己不构成模块。

**现在只实现第一期：** [05-v1-scope.md](./05-v1-scope.md)（用户、同好会创建与加入、活动、通知）。Wiki / Social / Program / Edge 以及 Club/Ops 里未列入 05 的部分一律冻结。

```text
                    ┌─ 用户中心 / 广场 / 社团详情 / 超管台 ─┐  ← 组合层，不是模块
                    │                                        │
┌──────────┐   ┌────┴─────┬─────────┬────────┬────────┬──────┴───┐
│  卫星    │   │ 同好会   │  运营   │  知识  │  社区  │ 赛事认可 │
│  Edge    │   │  Club    │  Ops    │  Wiki  │ Social │ Program  │
└────▲─────┘   └────┬─────┴────▲────┴────▲───┴────▲───┴────▲────┘
     │              │          │         │        │        │
     └──────────────┴──────────┴─────────┴────────┴────────┘
                           内核  Platform
                 本站会话 · 本站权限 · 通知 · 审计
              （登录借用 nextmoe OIDC，不自建账号）
```

---

## 为什么原站「分不动」

乱源只有四条，重构时对着拆：

1. **同好会是上帝对象。** 地图、会籍、活动、Wiki、投票、GalOnly、Bot、试炼全部直接抓 `clubs.json` 的字段。
2. **存储劈成两半。** 目录/活动/刊物/企划在 JSON 文件；账号/会籍/投票/论坛/试炼在 SQL。同一社团两边对 `(id, country)`。
3. **页面即应用。** 每个 HTML 自己拉 API、自己做权限、自己做主题。没有 BFF，也没有共享领域层。
4. **组合页吞噬边界。** 用户中心、同好会广场、社团详情把 5 个领域的卡片堆在一起，看起来像「一个功能」。

所以正确切法是：先规定 **每个模块只拥有哪些数据、对外只暴露什么 ID**，组合页只消费接口，不准直连别的模块的表或 JSON。

---

## 全局只共享两样东西

所有模块都允许依赖，除此之外禁止互相进库。

| 共享对象 | 形态 | 谁写 |
|----------|------|------|
| `User` | `user_id`（OIDC subject，整数 id） | 内核落表；身份由 nextmoe 签发 |
| `ClubRef` | `(club_id, country)` | 同好会模块 |

中日同编号必须成对出现，重构后也不许合成一套全局自增 ID。

会籍角色、代表同好会、联系方式是否可见，由 **同好会模块** 提供查询接口（例如 `CanManage(user, club)`、`PublicProfile(club, viewer)`），其他模块不准自己 join `club_memberships`。

---

## 内核 · Platform

不是产品功能，是所有模块的地板。第一期必须先立住，否则后面每个模块都会再抄一套登录。

vnfm **不是** nextmoe 下游。登录只做 OIDC Relying Party，借用 `account.nextmoe.com` 的账号；**本站权限完全由 vnfm 表决定**，IdP 的 `admin`/`ren` 不放行任何本站操作。禁止与 infra S2S。向 nextmoe 只借 OIDC，以及按需的 catalog。图床本站用 R2，不接 nextmoe image service。详见 [04-nextmoe-architecture.md](./04-nextmoe-architecture.md)。

| 拥有 | 不拥有 |
|------|--------|
| 本站会话（OIDC 换票之后） | 注册、改密、QQ/Discord、用户主档（账户中心） |
| 本站用户行（主键 = OIDC `id`）和本站 RBAC | nextmoe 全局角色作为授权依据 |
| 本站封禁/能力开关 | 账户中心封禁策略 |
| 通知发送管道、未读数 | 通知文案里的业务链接如何生成（各模块自己发） |
| 本站图床（R2 对象 + key 元数据）、壁纸、主题、语言偏好 | nextmoe 图床；地图、Wiki 正文 |
| 审计日志、限流、超管壳子、全站公告基础设施 | 具体审核队列的业务（各模块往壳子里挂） |
| | 会籍规则（字段可在 users 表，规则在 Club） |

对应原站：`api/auth.php`、`users.php`、`avatar.php`、`notifications.php`、`backgrounds.php`、`includes/mailer.php`、`rate_limit.php`、`audit.php`、主题/i18n 运行时。

Nuxt 侧：登录跳转/回调、用户中心「本站偏好 / 通知」骨架、全站 layout。账户资料链到 nextmoe 账户中心。  
Fiber 侧：`/auth`（OIDC 回调与本站会话）、`/users/me`、`/notifications`、`/media`。

## 模块 1 · 同好会 Club

原站真正的主产品。地图只是这个模块的一种视图。

**一句话：** 世界上有哪些同好会、它们在哪、资料是什么、谁属于它。

### 收进来

- 中国 / 日本 / 江苏地图与列表发现
- 社团目录与资料字段、头像、多省份、类型、保护模式
- 会籍申请、绑定码、角色、踢人、转让负责人、外交成员
- 联系方式可见性、资料完整度、公开分享卡
- 社团详情上的留言板、神器榜、萌王位
- 联合星图与星盟（`star_unions`）
- 负责人后台里「成员 / 设置 / 绑定码」那些页签
- 新社团投稿审核（`submit.html`）

### 不要收

- 活动、刊物、企划、Wiki 正文（只提供「这个社团是否存在、当前用户能否管理」）
- 投票、试炼、GalOnly 表单
- 论坛帖子

### 对外接口（其他模块只准走这些）

- 解析 `ClubRef` → 公开资料（已按查看者脱敏）
- `IsMember` / `CanManage` / `ListManagedClubs`
- 代表同好会读写（给论坛作者栏、用户中心用）
- 社团被删除/隐藏时的事件，供下游停用

重构第一期的业务模块就是它。做完之后，原站「能找组织、能加入」这条主路径就通了。

## 模块 2 · 运营 Ops

同好会「办事情」的模块。四块看起来不像一类，但共享同一套模式：**社团发起 → 配置表单 → 用户提交 → 负责人审核 → 状态机**。

| 子域 | 原站 | 备注 |
|------|------|------|
| 活动 | 日历、报名、`submit_event` | 通用活动 |
| 刊物 | 征稿、稿件、录用状态 | 和「资料公开库」不是一回事 |
| 企划枢纽 | 项目 / 参与项 / 文件 | 现在是 JSON 文件锁，重写时入库 |
| GalOnly | 摊位两阶段审核、Staff 招募、陪审 | 季节性、表单极重，**做成运营下的活动类型**，用活动配置驱动表单，禁止再按城市复制 HTML |

超管审核中心里的「活动申请 / 企划申请 / 刊物申请」挂在这里，不单开「审核模块」。

GalOnly 如果后期体量继续膨胀（多城、多届、独立品牌），再升格为独立模块；现在升格只会让第一期范围爆炸。

---

## 模块 3 · 知识 Wiki

只放 **可公开阅读、可沉淀的长内容**。

- 社团百科页（中日双语、信息框、章节、图、参考文献）
- 使用文档 Guide（主站 / 运营 / MakoQuiz / AstrBot）
- 资料公开库（已出版刊物的 PDF/图片存档 + 3D 阅读器）

征稿中的稿件（未出版、有审核流）留在运营模块。公开库是「已发布的成品」，百科是「结构化介绍」，Guide 是「产品说明书」。三者都是文档，读写模型接近：结构化存储 + 生成或渲染阅读页。

权限仍然问 Club：`CanManage` 才能编辑对应社团 Wiki。

---

## 模块 4 · 社区 Social

人与人之间的公开对话，不从属于某一个社团的内部流程。

- 论坛广场（发帖、回复、Markdown、附件、点赞、收藏、举报、置顶精华）
- 全站公告的 *发布与展示*（管道在内核，内容运营在这里或超管壳）
- 同好会广场、用户中心总览里那些「动态流」——它们是本模块的阅读面，数据仍来自别的模块

原站论坛已经物理隔离在 `Forum/`，而且主动砍掉了社团分区。重构时保持这点：**论坛不读社团目录，只读用户的代表同好会。** 这是原站少有的干净边界，不要再把 `scope=club` 做回去，除非单独开一期。

社团详情留言板更像 Club 的小插件，留在模块 1，不要塞进论坛。否则详情页还要依赖整个 Forum。

---

## 模块 5 · 赛事与认可 Program

所有「有报名、有阶段、有结果、会发名次或徽章」的东西。原站拆成萌战 / 十二器 / 试炼 / Quiz 四摊代码，其实是一类问题。

| 子域 | 本质 |
|------|------|
| 投票底座 | 通用阶段引擎（提名 → 海选 → 分组/对阵 → 结算） |
| 十二器 | 底座 + 作品条目 + Bangumi/VNDB |
| 萌战 | 底座 + 角色条目 + 1v1 对阵图 |
| 同好会试炼 | 规则版本化 + 凭证签发 + 公开核验 |
| MakoQuiz 连携 | 外部答题结果作为试炼事件进来 |

十二器和萌战 **禁止再做两套状态机**。试炼不要复用投票表，但和投票共享「资格（谁能参加）问 Club」这一条。

凭证（徽章）是本模块的核心资产：签发、撤销、过期、公开验证。Quiz 只是一种事件源。

## 卫星 · Edge

能从主站卸掉、单独部署或继续当静态子应用的东西。主站只提供入口链接和必要时的账号。

| 卫星 | 和主站的关系 |
|------|----------------|
| Galgame 同好会模拟器 | 几乎无耦合，Nuxt 用子路径托管即可 |
| 运行画像 | 可读 Club 预填，LLM 在自己的服务里 |
| AstrBot / 社团 Bot Token | **读** Club/Ops/Program 的公开查询接口，不进别人的库 |
| Bangumi / VNDB 代理 | Program 和 Club 神器榜的适配器，可放 Edge 或 Platform |
| 橘柚海龟汤等专题页 | 一次性运营页，不要进业务模块 |
| Electron / APK 壳 | 先不做 |

Bot 容易被误当成模块 1 的一部分。不要：Bot 是多个模块的只读外观，Token 签发可以放在 Club 负责人后台，查询实现必须走各模块 API。

## 明确不是模块的东西

重构时看到这些，当成 **组合层或基础设施**，不要新开仓库/新开服务。

| 东西 | 归宿 |
|------|------|
| 用户中心 | 组合层：骨架属 Platform，各 Tab 向 1–5 要数据 |
| 同好会广场 | 组合层：卡片聚合 Ops + Program + Edge |
| 社团详情页 | 组合层：主体属 Club，活动/Wiki/赛事用嵌入块 |
| 超级管理控制台 | Platform 的壳 + 各模块注册审核队列 |
| 主题 / i18n / 顶栏 / 壁纸 | Platform |
| 反馈建议 | Platform 或超管壳，别单独做模块 |
| `01` `02` `03` 文档 | 功能对照清单，不是目录结构 |

## 建议落地顺序

按依赖，不按「好不好看」。

```text
0  Platform     OIDC 换票、本站会话与权限、通知、layout
1  Club         地图 + 目录 + 会籍     ← 第一期可上线的最小产品
2  Ops          活动日历即可先做；刊物 / 企划 / GalOnly 按需追加
3  Wiki         百科阅读可先于编辑器
4  Social       论坛几乎可并行（只依赖 Platform + 代表同好会）
5  Program      底座先于十二器/萌战；试炼可再晚
6  Edge         随时可挂，不挡主路径
```

论坛（4）和 Wiki（3）在 Club 稳定后都可以并行。GalOnly、对阵图、试炼连接器是各自模块里的深水区，不要和「日历能报名」绑在同一期。

仓库里以后建议按模块建目录，而不是按 `01/02/03` 或按原站 HTML 文件名，例如：

```text
apps/web/          Nuxt 组合层
apps/api/          Fiber 入口
internal/platform/
internal/club/
internal/ops/
internal/wiki/
internal/social/
internal/program/
internal/edge/
```

每个 `internal/*` 对外只导出 API 与事件，禁止 `ops` import `wiki` 的表结构。
